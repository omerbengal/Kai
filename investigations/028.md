# תחקור 028 — המורנינג בריף מגיע ב-09:32 ולא ב-09:00

**תאריך:** 2026-05-10
**טריגר:** למה המורנינג בריף מגיע באופן עקבי ב-09:32 (ולא ב-09:00 כמו שמוגדר בקרון `0 9 * * *`)?

האיחור עקבי מאוד: **31.8–32.8 דקות**. שונות של פחות מדקה. זה לא רעש של jitter, זה דטרמיניסטי.

## מה קרה

הקרון `0 9 * * *` מוגדר נכון ל-09:00 ת"א, אך הבריף נשלח עקבית כ-32 דקות מאוחר יותר. הקרון עצמו יורה בזמן (Claude Code's cron) — מה שלוקח 32 דקות זה **ריצת agent הבריף עצמו**, לא דחיית הקרון.

הוכחות:

### א. ה-heartbeat לא חוסם את ה-REPL
`scripts/heartbeat.py` רץ דרך **Windows Task Scheduler** — תהליך חיצוני, לא קרון בתוך Claude Code. ה-`heartbeat_daytime_cron_id` שעדיין רשום ב-`.kai_cron_ids` הוא **שאריות מתועדת** (CLAUDE.md: "do NOT register it as a cron"). הוא בכלל לא נוצר בכל סשן חדש כי SessionStart לא מבקש זאת — רק `morning_briefing_cron_id` נרשם מחדש בכל סשן.

הוכחה אמפירית: בלוג `action_log` מ-2026-05-10:
```
05:55:05 → 06:34:04 — heartbeat ('run', 'ok') בכל דקה ברצף, ללא חורים.
06:32:24 → morning_briefing ('briefing_sent')
```
לולאת ה-heartbeat **רצה ב-06:00:05 UTC = 09:00:05 ת"א בדיוק**, מה שמוכיח שה-OS פעיל ושום דבר לא חוסם את הסביבה ב-09:00.

### ב. ה-cron יורה ב-09:00 — ה-agent הוא זה שלוקח 32 דקות
ה-launcher (`agents/morning_briefing_launcher.md`) הוא קצרצר — קורא קובץ ומפעיל `Agent(prompt=..., run_in_background=True)`. ה-Agent שמופעל מקבל את כל `agents/morning_briefing.md` כפרומפט, ועושה:

| שלב | פעולה | זמן מוערך |
|---|---|---|
| 0 | Dedup check (SQL) | ~1s |
| 0.5 | חישוב תאריך (Python subprocess) | ~2s |
| 1–5 | שאילתות SQL: tasks, overdue, high-priority, reminders, birthdays (5 פעולות נפרדות) | ~5–10s |
| 6 | מזג אוויר Open-Meteo (curl + Python parse) | ~3–8s |
| **6b** | **חיפוש web לחגים/יום זיכרון ישראלי** (חובה — לא להסתמך על ידע פנימי) | **~10–60s** |
| 7 | Google Calendar MCP — `list_events` להיום | ~5–15s |
| 8 | Gmail MCP — `is:unread in:inbox` עד 50 תוצאות + קטגוריזציה | **~20–60s** |
| 9 | חיבור ההודעה + שליחה ב-`reply` | ~2–5s |
| 10 | INSERT ל-action_log | ~0.5s |

**סה"כ צפוי: 1–3 דקות.** אבל הריצה בפועל לוקחת ~32 דקות. למה?

### ג. ה-Agent כותב סקריפטים זמניים ל-`tmp/` במקום inline
ראיה חזקה ב-`D:/Kai/tmp/`:

```

-rw-r--r-- 1512 May  5 09:32 briefing_msg.txt

-rw-r--r-- 1378 May  6 09:32 briefing_text.txt
-rw-r--r--  480 May  6 09:31 briefing_weather.py
```

קבצים שנוצרו על-ידי ה-Agent בריצה — `briefing_query.py` (DB), `briefing_weather.py` (curl), `briefing_send.py` (compose+reply), `briefing_log.py` (action_log INSERT). זה אומר שה-Agent לא מבצע את השלבים inline ב-Bash אלא:
1. כותב קובץ Python עם `Write`
2. מריץ את הקובץ עם `Bash`
3. כותב קובץ זמני נוסף עם הפלט (`briefing_text.txt`)
4. כותב את `briefing_send.py` שקורא את `briefing_text.txt`
5. וכן הלאה

כל סבב כזה (Write → Bash → Read) הוא round-trip של מודל-ל-tool ובחזרה, וכל round-trip של opus-4-7 לסוכן רקע יכול לקחת 1–3 דק' בקלות.

אישור: בקובץ `briefing_send.py` משלישי 6/5, ראיתי את כל ה-emails composed inline (קווים #31–37). זה לא קריאת MCP — זה Python שהמודל כתב אחרי שעשה את כל קריאות ה-MCP בנפרד.

## למה זה קרה (Root Cause)

**הסיבה השורשית: ה-agent של הבריף משתמש בארכיטקטורת "כתוב סקריפט → הרץ → קרא פלט → כתוב סקריפט הבא" במקום לבצע פעולות inline או batch אחד גדול.** כל סבב Write/Bash/Read של agent רקע (Opus) דורש round-trip שלם של inference + tool execution. כפול ~10 שלבים = ~30 דקות.

תורמים משניים:
1. **Step 6b — `web_search` חובה לכל בריף** (גם בימים שאין חג): מוסיף ~10–60s.
2. **Step 8 — Gmail MCP fetch של עד 50 מיילים + קטגוריזציה client-side** (במקום server-side filtering).
3. **חוסר חוזה זמן**: אין אזהרה ב-`morning_briefing.md` ש"השלם תוך X דקות" או הוראה לבצע צעדים במקביל / batched.
4. **ההגדרה "spawn background Agent"** מבטיחה שלא חוסם את הסשן הראשי, אבל גם אומרת שהמודל-בפנים רץ באופן סדרתי, צעד-אחר-צעד, באיטיות של agent ולא של inline Bash בסשן הראשי.

מה שלא הסיבה (פוסל את הפרשנויות הסבירות לכאורה):
- ❌ heartbeat — חיצוני, רץ ב-Task Scheduler, לא חוסם את ה-REPL.
- ❌ cron jitter — Claude Code docs מציינים מקסימום 15 דק', וגם זה היה משתנה בין ימים. שונות של < דקה דוחה את ההסבר הזה.
- ❌ daily_restart — פועל ב-06:00, 3 שעות לפני הבריף; גם אם כושל, לא מוסיף 32 דק' ב-09:00.
- ❌ הגדרת timezone — המכונה היא Israel Standard Time (UTC+3 DST פעיל). `cron="0 9 * * *"` מתפרש נכון.
- ❌ `.kai_cron_ids` שמציין heartbeat cron — שאריות תיעוד; לא מתבצעת רישום בפועל ב-SessionStart (רק morning_briefing).

## פתרון מוצע

### שינוי 1: `agents/morning_briefing.md` — איחוד שלבים 1–5 ל-script אחד inline

**לפני** (Steps 1–5): כל אחד מציג שאילתת SQL נפרדת עם הוראה "Use bash with Python's built-in sqlite3" → גורם ל-agent לכתוב `briefing_query.py`, להריץ, לקרוא, ואז לחזור עוד פעם לשלב הבא.

**אחרי**: בלוק יחיד מאוחד עם הוראה מפורשת:

```markdown
## Steps 1–5 — Bulk DB query (run as ONE Bash call, do NOT split)

⚠️ **PERFORMANCE: Run this entire block as a single inline `python -c "..."` call.
Do NOT write a separate .py file. Do NOT split into multiple Bash invocations.**
The whole bulk query must complete in one round-trip.

```bash
python -c "
import sqlite3, json, sys
from datetime import datetime, timezone, timedelta
sys.stdout.reconfigure(encoding='utf-8')
JLM = timezone(timedelta(hours=3))
now = datetime.now(JLM)
today_start = now.replace(hour=0,minute=0,second=0,microsecond=0).astimezone(timezone.utc).isoformat()
today_end = now.replace(hour=23,minute=59,second=59).astimezone(timezone.utc).isoformat()
seven = (now+timedelta(days=7)).astimezone(timezone.utc).isoformat()
conn = sqlite3.connect('D:/Kai/kai.db'); conn.text_factory=str
cur = conn.cursor()
out = {}
cur.execute('SELECT title,priority,strftime(\"%H:%M\",due_at,\"+3 hours\") FROM tasks WHERE status=\"open\" AND due_at BETWEEN ? AND ? ORDER BY priority DESC',(today_start,today_end))
out['tasks_today'] = cur.fetchall()
cur.execute('SELECT title,priority,CAST(julianday(\"now\")-julianday(due_at) AS INTEGER) FROM tasks WHERE status=\"open\" AND due_at < datetime(\"now\") ORDER BY priority DESC')
out['overdue'] = cur.fetchall()
cur.execute('SELECT id,title,priority,CAST(julianday(due_at)-julianday(\"now\") AS INTEGER) FROM tasks WHERE status=\"open\" AND priority>=10 AND due_at>datetime(\"now\") AND (julianday(due_at)-julianday(\"now\"))<=7 ORDER BY due_at')
out['high_pri_upcoming'] = cur.fetchall()
cur.execute('SELECT message,strftime(\"%H:%M\",trigger_at,\"+3 hours\"),date(trigger_at,\"+3 hours\") FROM reminders WHERE status=\"pending\" AND date(trigger_at,\"+3 hours\")<=date(\"now\",\"+3 hours\",\"+1 day\") ORDER BY trigger_at')
out['reminders'] = cur.fetchall()
cur.execute('SELECT name,birthday FROM people WHERE birthday IS NOT NULL')
out['people'] = cur.fetchall()
print(json.dumps(out, ensure_ascii=False))
"
```

Parse the JSON and use it for all subsequent composition. **Do not return to the DB.**
```

**סיבה:** מצמצם 5 round-trips ל-1. חוסך ~10–15 דקות.

### שינוי 4: `agents/morning_briefing.md` — הוספת "execution contract" בראש הקובץ

You are a background agent. Each Write/Bash/Read round-trip costs ~1–2 minutes.
