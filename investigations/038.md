**Date:** 2026-07-23
**Status:** ✅ Root cause proven with process-creation timestamps. Overturns #037's "reload triggered it" assumption and confirms the poller fixes (#033–#036) targeted a process that wasn't even alive.

## What this proves

1. **The bun poller does not exist during the dead window.** CC did not spawn it until 06:38:43. So every fix that manipulated the bun poller / 409 retry / orphan-killing (#033 kill-orphans, #034 parent-liveness, #035 never-give-up-409, #036 async-hook) operated on a process that isn't running in the window where messages are lost. They could never have fixed this.

2. **Normal `mcpServers` connect in ~2 s; the `--channels` plugin connects minutes later.** Same session, same startup. The delay is specific to the channel-plugin connection path, not general MCP startup and not a slow queue (the others all finished at 06:33:56).

3. **reload-plugins is what spawns bun. (Omer confirmed, verbatim: "הכניסה של טסט קרתה כי אני הרצתי reload plugins לבד. אני הרצתי.")** So the 06:38:43 spawn was Omer's manual reload, NOT a spontaneous auto-connect. Corrected from an earlier over-claim in this session that CC auto-connects after ~5 min — there is NO evidence CC ever spawns the channel bun at startup. The connect_watcher experiment timed out ("no new session detected in time") precisely because nothing connected until Omer reloaded. **Working conclusion: CC does not spawn/connect the `--channels` telegram plugin at session start at all; a manual reload-plugins is currently required every restart.**

4. **Not a Kai regression in code.** All Kai patches to server.ts sit AFTER `await mcp.connect(...)` (line 661) — runtime handlers, not the pre-connect path. All three SessionStart hooks are trivial: `session_handoff_notify.py` only prints; the other two are `async: true`. None block CC for minutes.

## Why "it used to work" (Omer's memory)

Most consistent with the era when Telegram was a regular `mcpServers` entry (`D:/Kai/.venv/Scripts/telegram-mcp-server.exe`, still in settings.json but now DEAD — no process, no mcp-logs dir, CC ignores it because the channel is loaded via `--channels plugin:telegram@claude-plugins`). Regular mcpServers connect in ~2 s (proven above). Switching the integration to the plugin-**channel** architecture is what introduced the multi-minute connect delay. This is CC-internal behavior for channel plugins, not something a server.ts patch caused.

## Delay is variable (54 s – 5 min across sessions)

Variable, not a fixed timeout → CC connects the channel after some startup phase of variable duration (likely after the heavy startup-context / first-idle). Cannot be reconfigured from Kai side in this CC version.

## Correct path forward (Phase 4.5 — architectural, not another poller patch)

STOP patching the poller. The channel-connect timing is owned by CC. Realistic options:
- **A. External connect signal (recommended):** a watcher OUTSIDE CC (connect_watcher.py) that tails the plugin mcp-log, detects the real "Successfully connected" line, and pings Omer directly via the bot API — "I'm live now, send away." Removes the guessing; Omer stops needing reload-plugins as a ritual.
- **B. Accept + inform:** restart flow tells Omer "~a few minutes to connect, messages queue and flush automatically — don't touch reload-plugins." Honest, poor UX.
- **C. Auto-force connect:** if a reload-plugins equivalent can be triggered at startup (startup slash-command / programmatic reload). Needs verification it exists in this CC build.

## CONFIRMED: upstream Claude Code bug (claude-code-guide research, 2026-07-23)

Channel plugins passed via `--channels plugin:...` are DOCUMENTED to auto-connect at startup, but multiple public bug reports confirm they do not in practice (Windows notably affected). Channels are a "research preview" feature with special, buggy startup handling — distinct from `mcpServers`, which the core harness spawns during init (hence the ~2 s connect for Gmail/Calendar/etc.). `/reload-plugins` triggers a re-scan that works around the startup bug. `--rc` (= `--remote-control`) is for driving the session from claude.ai/phone, NOT external command injection; there is no documented IPC/stdin/socket to trigger `/reload-plugins` from a script. No flag forces eager channel connection. => We cannot fix the cause (upstream); only a zero-touch workaround.

## FIX APPLIED (workaround): initial-prompt auto-reload

`start_claude.bat` now launches CC with `"/reload-plugins"` as the initial positional prompt:
`claude.exe ... --channels ... --rc "/reload-plugins"`
CC runs the slash command the instant the session starts → forces the channel to connect with zero manual action from Omer. Reversible (remove the arg). Becomes a harmless no-op if the upstream bug is ever fixed.

**Verification:** next restart is the live test. Success criterion = plugin mcp-log shows "Starting connection" within seconds of session start (not minutes), and inbound messages arrive without Omer touching reload-plugins. connect_watcher.py pings on connect. If the positional slash command is NOT auto-executed (only prefilled), fall back to SendKeys of "/reload-plugins{ENTER}" from restart_claude.ps1 after the new session is detected.
